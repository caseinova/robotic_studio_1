A / MODELLING · 20 MARKS

Robot and observer models.

Forward kinematics

Six revolute joints: q ∈ ℝ⁶. Hardware uses standard DH; simulation uses the MuJoCo model.

θᵢ = qᵢ + offsetᵢ
Aᵢ(qᵢ) = Rᶻ(θᵢ) Tᶻ(dᵢ) Tˣ(aᵢ) Rˣ(αᵢ)
ᵂTₜ(q) = ᵂTᵦ · (∏ᵢ₌₁⁶ Aᵢ(qᵢ)) · ᶠTₜ
ᵂT𝗀(q) = ᵂTₜ(q) · ᵀT𝗀

Implementation, hardware/hardware_kinematics.py:

for theta, a, d, alpha in zip(q + offsets, dh.a, dh.d, dh.alpha):
    ct, st = np.cos(theta), np.sin(theta)
    ca, sa = np.cos(alpha), np.sin(alpha)
    link = np.array([[ct, -st*ca,  st*sa, a*ct],
                     [st,  ct*ca, -ct*sa, a*st],
                     [ 0,     sa,     ca,    d],
                     [ 0,      0,      0,    1]])
    chain.append(chain[-1] @ link)
world_from_tool = chain[-1] @ flange_from_tool

Here c and s abbreviate cos and sin of θᵢ or αᵢ. DH values and installation transforms must match the physical arm.

Velocity model

ᵂVₜ = J(q) q̇,     Jᵢ = [ zᵢ₋₁ × (pₜ − pᵢ₋₁) ; zᵢ₋₁ ]
ᵀVₜ = diag(Rᵀ, Rᵀ) ᵂVₜ,     R = ᵂRₜ

Hardware computes revolute-joint columns; simulation obtains the Jacobian from MuJoCo. Approach uses the tool-local Jacobian.

linear = np.cross(axes.T, (tool[:3, 3, None] - origins).T).T
rotation = tool[:3, :3].T if local else np.eye(3)
J = np.vstack((rotation @ linear, rotation @ axes))

Discrete prediction and rank

The optional MPC assumes velocity tracking over each interval; it is not a rigid-body dynamics model.

qₖ₊₁ = qₖ + Δt uₖ,     yₖ = qₖ
A = I₆,     B = Δt I₆,     C = I₆
𝒞 = [B  AB  ⋯  A⁵B],     𝒪 = [C; CA; ⋯; CA⁵]
rank(𝒞) = rank(𝒪) = 6  (Δt > 0)
σᵢ(𝒞) = √6 Δt,     σᵢ(𝒪) = √6  (i = 1, …, 6)

For Δt = 0.05 s: σᵢ(𝒞) ≈ 0.1225, σᵢ(𝒪) ≈ 2.4495; both condition numbers are 1 in these coordinates. These ranks do not guarantee Cartesian reachability, collision-free motion or physical tracking.

integration = np.kron(np.tril(np.ones((horizon, horizon))) * dt,
                      np.eye(6))
q_predicted = np.tile(q, horizon) + integration @ u

The code constructs the same stacked prediction inside JointSpaceMPC; q is measured at the start of each solve.

Cube observer

x = (p, R, v, ω),     δx = [δpᵀ δθᵀ δvᵀ δωᵀ]ᵀ ∈ ℝ¹²
pₖ₊₁ = pₖ + Δt vₖ,     Rₖ₊₁ = Exp([ωₖ]× Δt) Rₖ
vₖ₊₁ = vₖ,             ωₖ₊₁ = ωₖ

For one locally linearized translation axis with pose measurements:

Aₚ = [1  Δt; 0  1],     Cₚ = [1  0]
𝒪ₚ = [Cₚ; CₚAₚ] = [1  0; 1  Δt],     det(𝒪ₚ) = Δt

Thus rank(𝒪ₚ) = 2 when Δt ≠ 0. Rotation uses a local error-state linearization; accepted measurements and valid calibration are assumed. This is not a global nonlinear observability result.

B / SENSING · 20 MARKS

One frame convention, end to end.

RGB-D marker processing validates depth and geometry, transforms visible cube faces to a common cube frame, rejects inconsistent measurements, and fuses accepted faces. One visible cube face is sufficient. DICT_4X4_50 IDs 0 and 2–6 identify cube faces; ID 1 identifies the tool. Dimensions and mounting transforms must match the physical installation.

World W ← Camera C ← Marker M ← Cube
World W ← Robot base B ← Flange F ← Tool T ← Tool marker

Each arrow maps the frame on its right into the frame on its left. A_from_B maps coordinates from B into A.

W_from_cube = W_from_camera · C_from_marker · M_from_cube
C_from_tool = C_from_tool_marker · inverse(T_from_tool_marker)
T_from_cube = inverse(C_from_tool) · C_from_cube

When both tags are observed, the relative tool-to-target measurement cancels camera-to-world extrinsics algebraically. Encoder FK still supplies Jacobians and collision prediction. This does not remove marker mounting, depth, timing or intrinsics errors.

Hardware workflow: import RealSense intrinsics; verify tag dimensions; collect stationary, diverse tool-tag poses; solve camera-to-base and tool-tag transforms jointly; inspect held-out errors; independently verify known poses. The collector recommends at least 12 distinct poses, preferably 15–25 or more. It does not calibrate the grasp TCP automatically.

Calibration evidence required: actual intrinsics / distortion, frame transforms, sample count, held-out translation and rotation error, sensor noise measurements and installation diagram or photo.

C / ESTIMATION · 20 MARKS

Pose estimates with uncertainty.

The cube error-state EKF predicts constant linear / angular velocity and corrects with fused visual pose measurements. Covariance is ordered [δp, δθ, δv, δω]. The tool filter is configured to predict using FK increments and correct with accepted tag poses; it is not an online camera-calibration estimator.

P⁻ = F P Fᵀ + Q
K = P⁻ Hᵀ (H P⁻ Hᵀ + R)⁻¹
Q_axis = σa² [[Δt³/3, Δt²/2], [Δt²/2, Δt]]

Cube prediction expires 0.3 s after the last accepted measurement. Tool FK-increment fusion also enforces uncertainty and correction bounds; expiry latches a hold. Missing / stale estimates are not replaced with simulator truth. Covariance bands express filter uncertainty, not guaranteed physical error.

Evidence required: justify Q and R from measurements; compare raw and filtered pose RMSE, transient lag and uncertainty coverage; show behavior during lost tags. Include plots from submitted runs, not illustrative curves.

D / CONTROL · 20 MARKS

Visual feedback, constrained motion.

PBVS forms a tool-frame translation and rotation error and maps a bounded tool twist through a damped Jacobian inverse. The optional joint-space MPC tracks that reference over a finite horizon.

u_ref = Jᵀ (J Jᵀ + λ² I)⁻¹ · bounded(gain · e)
MPC cost = Σ (w_tracking ‖u − u_ref‖² + w_smoothing ‖u − u_prev‖²)

The checked-in controller selects pure_pbvs. This mode does not run MPC obstacle or self-collision clearance checks during approach. Pickup and placement have separate guards. MPC is available, but must not be reported as the evaluated controller unless it was enabled in the saved run configuration.

Optional MPC defaults: Δt 0.05 s, horizon 8, tracking weight 1.0, smoothing weight 0.15, velocity limit 0.35 rad/s, acceleration limit 1.5 rad/s², clearance 0.015 m plus a 0.003 m buffer. Backend and runtime settings can override these values. These are configuration values, not measured performance or a tuning justification.

Pickup proceeds through approach, dwell, descent, close and lift. Placement acquires one fresh destination pose, then latches it for raise, transfer, descent, release and retreat. The marker and camera must remain stationary after acquisition. A blocked local route stops rather than finding a global detour.

Add gain / weight selection rationale, tracking error and settling time, command effort, limits reached, and PBVS versus MPC comparison if evaluated.

REPRODUCIBILITY

Start with simulation.

Run from the repository root. The supplied guide targets Ubuntu and Python 3.12. MuJoCo rendering needs a working graphics backend, including for headless RGB-D perception.

git clone https://github.com/caseinova/robotic_studio_1.git
cd robotic_studio_1
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
python run.py --backend simulation --task pick --validate
python run.py --backend simulation --task pick
python run_sequence.py drop_zone_b --backend simulation --validate
python run_sequence.py drop_zone_b --backend simulation

Windows: use venv\Scripts\activate. For the desktop launcher, install requirements-gui.txt and run python run_experiments.py. For software checks, install pytest and run python -m pytest tests; some tests require additional rendering or device dependencies.

Always specify --backend simulation: the sequence CLI otherwise defaults to hardware. To vary trials, change cube position / quaternion in config/simulation_config.json and the seed / noise in config/noise_config.json; save each exact configuration and restart the run. Do not treat random measurement noise as random object placement.

Hardware is a separate installation workflow.

This is research software, not a safety-rated controller. Follow hardware setup and calibration before motion. Keep the physical emergency stop available and verify stopping on the pendant. The desktop Stop button is cooperative software shutdown.
