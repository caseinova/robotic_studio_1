Pick & place.

This project uses a UR3e arm and an OnRobot RG2 gripper to locate a tagged cube, pick it up and place it at a second marker. A fixed RGB-D camera provides colour and depth images for measuring object poses, while robot encoders provide joint feedback.

Reading guide: the page follows the measurement-to-motion pipeline. The notation table at the bottom defines the mathematical symbols, their context and units.

UR3e + RG2RGB-D / ArUcoEKF + PBVSMuJoCo
Fixed-camera installation

The camera observes the workspace from a fixed external position (eye-to-hand). Simulation and hardware share perception and control code, but hardware requires its own camera calibration, tool transforms and collision geometry.

RGB-D + encoders→Pose fusion + EKF→PBVS / optional MPC→Grasp + place

Engineering approach

The central problem is to turn noisy, sometimes missing visual measurements into bounded robot motion. To establish geometric references, we use ArUco markers: square binary patterns with identifiable IDs and known dimensions. An extended Kalman filter (EKF) then combines the accepted observations with a motion model, and position-based visual servoing (PBVS) uses the resulting pose estimate to reduce the remaining error. When additional constraints are needed, optional model predictive control (MPC) accounts for joint limits and clearance over a short horizon. Finally, a phase-based action controller coordinates opening, descent, gripping, transport and release, since each operation requires different completion and contact checks.

To test this pipeline, MuJoCo provides a simulated robot, camera and contact environment, while hardware adapters allow the same high-level perception and action code to operate on the physical system. Separating the application from its backend therefore supports controlled tests of sensing and estimation. It does not, however, imply that the simulated contact behaviour or nominal geometry exactly matches the physical installation.

Ground-truth simulator poses are recorded for evaluation, not supplied as visual measurements to the controller. See interface, controller and telemetry.

Demonstration

A demonstration video has not yet been published on this page. The sections below explain the implementation and present archived simulation results. These examples do not establish a general success rate.

MODELLING

Robot and observer models.

Because the application commands joint velocities rather than motor torques, we use a kinematic model to relate the measured joint angles to the tool pose and Cartesian motion. The backend handles low-level actuation, which keeps the online model small. This simplification nevertheless assumes that the commanded velocities are tracked sufficiently well over each control interval.

Forward kinematics

The UR3e has six revolute joints, represented by q \in \mathbb{R}^6. On hardware, the controller calculates the tool pose using standard Denavit–Hartenberg (DH) parameters, whereas in simulation it uses the MuJoCo robot model. In either case, forward kinematics (FK) gives the pose of the tool reference frame, and a separate rigid offset locates the grasp point between the fingers. Consequently, a change in the finger geometry can be represented as a tool offset rather than a change in the arm model.

\begin{aligned} \theta_i &= q_i + \mathrm{offset}_i \\ A_i(q_i) &= R_z(\theta_i)\,T_z(d_i)\,T_x(a_i)\,R_x(\alpha_i) \\ {}^W T_T(q) &= {}^W T_{\mathrm{base}} \left(\prod_{i=1}^{6} A_i(q_i)\right) {}^F T_T \\ {}^W T_G(q) &= {}^W T_T(q)\,{}^T T_G \end{aligned}

The following simplified excerpt from hardware/hardware_kinematics.py builds the hardware transform chain:

for theta, a, d, alpha in zip(q + offsets, dh.a, dh.d, dh.alpha):
    ct, st = np.cos(theta), np.sin(theta)
    ca, sa = np.cos(alpha), np.sin(alpha)
    link = np.array([[ct, -st*ca,  st*sa, a*ct],
                     [st,  ct*ca, -ct*sa, a*st],
                     [ 0,     sa,     ca,    d],
                     [ 0,      0,      0,    1]])
    chain.append(chain[-1] @ link)
world_from_tool = chain[-1] @ flange_from_tool

In this excerpt, ct, st, ca and sa are the corresponding cosine and sine values. DH values and installation transforms must match the physical arm.

Velocity model

Once the tool pose is known, the controller also needs to relate joint motion to tool motion. The Jacobian provides this local velocity relationship:

\begin{aligned} {}^W V_T &= J(q)\dot q, & J_i &= \begin{bmatrix}z_{i-1}\times(p_T-p_{i-1})\\z_{i-1}\end{bmatrix} \\ {}^T V_T &= \operatorname{diag}(R^\top,R^\top)\,{}^W V_T, & R &= {}^W R_T \end{aligned}

The hardware implementation calculates a Jacobian column for each revolute joint, while the simulation obtains the Jacobian from MuJoCo. During approach and transfer, the Jacobian and pose error are both expressed in the tool frame so that the requested translation and rotation use the same axes. Here, changing the expression frame rotates the axes used to express the twist without moving its origin.

linear = np.cross(axes.T, (tool[:3, 3, None] - origins).T).T
rotation = tool[:3, :3].T if local else np.eye(3)
J = np.vstack((rotation @ linear, rotation @ axes))

Discrete prediction and rank

For prediction over several control intervals, the optional MPC integrates piecewise-constant joint-velocity commands. This extends the local kinematic model into a short-horizon trajectory, allowing the controller to predict joint-limit crossings and evaluate geometric clearance without identifying masses, inertias or actuator torques. Because the model remains kinematic, however, it cannot predict contact forces or compensate for arbitrary actuator dynamics.

\begin{aligned} q_{k+1} &= q_k + \Delta t\,u_k, & y_k &= q_k \\ A &= I_6, & B &= \Delta t\,I_6, \qquad C=I_6 \\ \mathcal C &= \begin{bmatrix}B & AB & \cdots & A^5B\end{bmatrix}, & \mathcal O &= \begin{bmatrix}C\\CA\\\vdots\\CA^5\end{bmatrix} \\ \operatorname{rank}(\mathcal C) &= \operatorname{rank}(\mathcal O)=6, & \Delta t &>0 \\ \sigma_i(\mathcal C) &= \sqrt6\,\Delta t, & \sigma_i(\mathcal O) &= \sqrt6,\quad i=1,\ldots,6 \end{aligned}

At \Delta t=0.05\,\mathrm{s}, every singular value of \mathcal C is approximately 0.1225 and every singular value of \mathcal O is approximately 2.4495. Both matrices therefore have a condition number of 1 in these coordinates: every joint-state direction is actuated and directly measured in this ideal model. Nevertheless, these joint-space properties do not guarantee Cartesian reachability, collision-free motion or accurate physical tracking.

integration = np.kron(np.tril(np.ones((horizon, horizon))) * dt,
                      np.eye(6))
q_predicted = np.tile(q, horizon) + integration @ u

The code constructs the same stacked prediction inside JointSpaceMPC, using the joint positions q measured at the start of each solve.

Cube observer

Unlike the arm, the cube has no encoder feedback, so its short-term motion must be inferred from successive camera observations. We use a constant-velocity model to describe that motion with few states, while process noise allows for departures from the approximation during manipulation or disturbances.

\begin{aligned} x &= (p,R,v,\omega), \qquad \delta x = \begin{bmatrix}\delta p^\top & \delta\theta^\top & \delta v^\top & \delta\omega^\top\end{bmatrix}^\top \in \mathbb R^{12} \\ p_{k+1} &= p_k+\Delta t\,v_k, \qquad R_{k+1}=\operatorname{Exp}([\omega_k]_\times\Delta t)\,R_k \\ v_{k+1} &= v_k, \qquad \omega_{k+1}=\omega_k \end{aligned}

For one translation axis, the following local linearization relates position and velocity to a position measurement:

\begin{aligned} A_p &= \begin{bmatrix}1 & \Delta t\\0 & 1\end{bmatrix}, & C_p &= \begin{bmatrix}1 & 0\end{bmatrix} \\ \mathcal O_p &= \begin{bmatrix}C_p\\C_p A_p\end{bmatrix} =\begin{bmatrix}1 & 0\\1 & \Delta t\end{bmatrix}, & \det(\mathcal O_p)&=\Delta t \end{aligned}

Thus \operatorname{rank}(\mathcal O_p)=2 when \Delta t\ne0. The corresponding rotation model uses a local error-state linearization. Both analyses assume accepted measurements and valid calibration, so the result should not be interpreted as a global nonlinear observability guarantee.

SENSING

RGB-D to robot frames.

The models above require measurements of both the cube position and its orientation. We obtain these from known square markers, which provide geometric references without requiring a trained object detector. Placing markers on several faces improves the chance that at least one remains visible, while the depth image provides a metric consistency check. In return, the method depends on the specified marker dimensions, mounting transforms and depth quality.

Measurements and projection

On hardware, the RealSense D435i aligns the depth image with the colour image, after which the hardware interface rectifies both images and converts the depth values to metres. The simulation supplies registered RGB-D images for the same processing pipeline, while joint positions are measured separately.

K_{\mathrm{cam}}=\begin{bmatrix}f_x & 0 & c_x\\0 & f_y & c_y\\0 & 0 & 1\end{bmatrix}, \qquad \rho=K_{\mathrm{cam}}^{-1}\begin{bmatrix}u_{\mathrm{px}}\\v_{\mathrm{px}}\\1\end{bmatrix}, \qquad {}^C p=z\rho

z is optical-axis depth, not Euclidean range. The processor also checks RGB and depth timestamps for skew and repeated frames. The IMU, meanwhile, is not used in this pipeline.

aligned = self.align.process(frames)
rgb = cv2.remap(sample.rgb, *maps, interpolation=cv2.INTER_LINEAR)
depth = cv2.remap(sample.depth.astype(np.float32) * depth_scale,
                  *maps, interpolation=cv2.INTER_NEAREST)

Marker pose

OpenCV detects markers from the DICT_4X4_50 dictionary, using AprilTag corner refinement and a subpixel fallback. The cube uses IDs 0 and 2–6, and the tool uses ID 1. The current hardware configuration specifies a 64 mm cube with 40 mm markers on both the cube and tool.

\begin{aligned} {}^C p_j &= R\,{}^M p_j+t, \qquad \hat u_j=\pi(K_{\mathrm{cam}}\,{}^C p_j) \\ e_{\mathrm{rms}} &= \sqrt{\frac14\sum_{j=1}^{4}\lVert\hat u_j-u_j\rVert^2} \end{aligned}

A perspective-n-point (PnP) solve first estimates pose from the known square and its image corners. To incorporate depth, the processor fits a plane to samples inside an eroded marker polygon, reducing contamination from the surrounding surface. It then intersects the corner rays with that plane to obtain metric 3D corners and refines the pose through a rigid fit based on singular value decomposition (SVD). Throughout this process, reprojection checks ensure that both the initial and refined poses remain consistent with the image.

\begin{aligned} n^\top p &= d, & p_j &=\frac{d}{n^\top \rho_j}\,\rho_j \\ \ell_j &=\lVert p_{j+1}-p_j\rVert, & |\ell_j-s| &\le 0.1s \end{aligned}

The fit requires at least 16 valid depth samples and at least 80% of the samples to be plane inliers. The plane tolerance adapts to depth scatter: the configured tolerance is its minimum, and the adaptive component is capped at 10% of the marker size. In addition, all four reconstructed edges must pass the size test. Together, these checks reject detections that resemble valid markers in the image but have inconsistent 3D geometry. Consequently, a bent tag or unreliable depth can interrupt tracking even when the marker ID is visible.

plane_tolerance = max(depth_tolerance,
                      min(3 * depth_sigma, marker_size * 0.1))
edge_lengths = np.linalg.norm(corners_3d - np.roll(corners_3d, -1, axis=0), axis=1)
if np.any(np.abs(edge_lengths - marker_size) > marker_size * 0.1):
    return reject("tag_metric_size_inconsistent")

Cube-face fusion and frames

Once the individual marker poses pass these checks, each accepted face is transformed to the cube centre using its mounting transform. Because that transform encodes both the marker orientation and its offset, an incorrect mounting specification introduces a bias before fusion even begins.

\begin{aligned} {}^C T_{B,i} &= {}^C T_{M_i}\,({}^B T_{M_i})^{-1}, & w_i &\propto \frac{\mathrm{area}_i}{1+e_i^2} \\ \bar p &= \sum_i w_i p_i, & \bar R &= \operatorname{proj}_{\mathrm{SO}(3)}\!\left(\sum_i w_iR_i\right) \end{aligned}

For fusion, the highest-weight face serves as the reference, and other faces contribute only if they agree with it within 20 mm and 0.35 rad. Additionally, the processor requires valid depth within the estimated cube volume. Although a single valid face can be sufficient, any accepted faces are combined into one measurement per frame for the EKF. This reduces dependence on a particular viewpoint, but it is not a majority vote: all faces share the same camera and may therefore share systematic errors. Nor can filtering rescue a frame in which every face fails the geometric checks.

\begin{aligned} {}^W T_B &= {}^W T_C\,{}^C T_B \\ {}^C T_T &= {}^C T_{M_T}\,({}^T T_{M_T})^{-1} \\ {}^T T_B &= ({}^C T_T)^{-1}\,{}^C T_B \end{aligned}

In these equations, W denotes the world, C the camera, B the cube, T the tool and M a marker. The transform {}^A T_B maps coordinates from frame B into frame A. A common camera-to-world error cancels in the last equation when both poses use the same camera transform, but FK fallback, timing errors and marker-mounting errors do not necessarily cancel.

Calibration

To connect these camera-frame measurements to the robot, the hardware calibration workflow first imports the camera's factory intrinsics and depth scale. It then pairs stationary tool-marker observations from diverse arm poses with robot joint measurements to solve the camera-to-world and tool-marker transforms. Varying both the arm position and orientation helps distinguish the fixed camera transform from the marker mounting transform, while held-out poses test consistency beyond the fitted samples. The grasp tool centre point (TCP), however, must be measured separately because the marker observations do not identify the finger contact location.

The checked-in hardware configuration defines the world frame at the robot base. Consequently, the camera-to-world and camera-to-base transforms are identical:

{}^W T_{\mathrm{base}}=I_4,\qquad {}^W T_C={}^W T_{\mathrm{base}}\,{}^{\mathrm{base}}T_C ={} ^{\mathrm{base}}T_C

The configured transforms below are rounded to six decimal places, with translations in metres. They describe this installation, not a calibration that can be reused on another setup.

{}^W T_C=\begin{bmatrix} 0.999996 & -0.002843 & -0.000915 & -0.073655 \\ -0.000826 & -0.557861 & 0.829934 & -0.804381 \\ -0.002870 & -0.829930 & -0.557861 & 0.489339 \\ 0 & 0 & 0 & 1 \end{bmatrix}
{}^T T_{M_T}=\begin{bmatrix} 0.999755 & -0.017503 & 0.013554 & 0.000851 \\ 0.013254 & -0.017181 & -0.999765 & -0.019749 \\ 0.017732 & 0.999699 & -0.016944 & 0.079651 \\ 0 & 0 & 0 & 1 \end{bmatrix}
{}^F T_T=I_4,\qquad {}^T p_G=\begin{bmatrix}0\\0\\0.195\end{bmatrix}\,\mathrm{m}

The tool-marker, flange-tool and tool-grasp transforms were measured for the installation. The flange-to-tool transform is the identity, and the grasp point is 195 mm along the tool's positive z-axis. The full-precision matrices remain in the hardware configuration.

In practice, calibration typically used around 20 stationary poses, with the tool marker moved from left to right across the camera image and presented at different orientations. This describes the usual collection procedure rather than a verified sample count for a published calibration dataset.

Although this procedure establishes the installation transforms, sensor noise was not measured, and no held-out calibration dataset is published with this page. We therefore make no numerical claim about calibration accuracy.

ESTIMATION

Pose estimates with uncertainty.

Even after the geometric checks and face fusion, the measured pose can jitter while the object is stationary. The EKFs address this temporal variation by combining a predicted pose with a visual correction, weighting their disagreement by covariance rather than simply averaging successive frames. We use separate cube and tool filters because their available motion information differs: the cube is observed only by the camera, whereas tool motion can also be predicted from joint encoders. Despite these different predictors, both filters estimate pose in world coordinates without using simulation ground truth.

Cube prediction

Following the motion model introduced earlier, the cube filter assumes constant linear and angular velocity between observations. It stores orientation as a rotation matrix rather than three Euler angles, while a small rotation-vector error provides a local, three-dimensional representation for the covariance. This avoids Euler-angle singularities and, together with position and both velocities, gives a 12-dimensional error state:

\begin{aligned} x &= (p,R,v,\omega), \qquad \delta x=\begin{bmatrix}\delta p^\top & \delta\theta^\top & \delta v^\top & \delta\omega^\top\end{bmatrix}^\top \\ R_{\mathrm{true}} &= \operatorname{Exp}([\delta\theta]_\times)\,R \\ p^- &= p+hv, \qquad R^-=ER,\qquad v^-=v,\qquad \omega^-=\omega \\ \varphi &=h\omega,\qquad E=\operatorname{Exp}([\varphi]_\times) \end{aligned}
F=\begin{bmatrix} I_3 & 0 & hI_3 & 0\\ 0 & E & 0 & hJ_l(\varphi)\\ 0 & 0 & I_3 & 0\\ 0 & 0 & 0 & I_3 \end{bmatrix},\qquad P^-=FPF^\top+Q

Here, [\cdot]_\times is the cross-product matrix and J_l is the \mathrm{SO}(3) left Jacobian. The implementation divides each elapsed interval into steps of at most 0.05 s to keep the rotation linearization local. For each position–velocity or orientation–angular-velocity axis, it adds the following process covariance:

Q_{\mathrm{axis}}=\sigma_a^2\begin{bmatrix} \dfrac{h^3}{3} & \dfrac{h^2}{2}\\[6pt] \dfrac{h^2}{2} & h \end{bmatrix}

The linear and angular acceleration-noise parameters supply \sigma_a independently. Before prediction can begin, the first valid cube observation initializes the position and orientation, while both velocities start at zero. Accordingly, the initial pose covariance comes from the measurement variances, whereas the initial velocity covariance comes from the configured velocity standard deviations.

Tool prediction from FK increments

For the tool, encoder feedback provides a more direct motion predictor. With prediction_model = fk_increment and the shared tag-with-FK tracker enabled, the filter maintains one pose estimate and a six-dimensional error covariance. Rather than supplying an absolute pose at every step, FK supplies the motion increment, so a briefly hidden tag does not force a jump to a potentially offset absolute FK pose. Instead, the visually corrected estimate advances with the measured arm motion as follows:

\begin{aligned} \delta x_T &=\begin{bmatrix}\delta p^\top & \delta\theta^\top\end{bmatrix}^\top\\ \Delta T_k &=(T_{\mathrm{FK},k-1})^{-1}T_{\mathrm{FK},k}\\ \hat T_k^- &=\hat T_{k-1}\Delta T_k\\[4pt] F_T &=\begin{bmatrix}I_3 & -[\hat R_{k-1}\Delta p_k]_\times\\0 & I_3\end{bmatrix}\\ Q_T &=\Delta t\,\operatorname{diag}(\sigma_{\mathrm{FK},p}^2 I_3,\sigma_{\mathrm{FK},\theta}^2 I_3)\\ P_T^- &=F_T P_T F_T^\top+Q_T \end{aligned}

The translation \Delta p_k belongs to the body-local increment \Delta T_k. At startup, a fresh tool-tag observation initializes the pose if one is available. Otherwise, FK supplies the initial pose. Subsequent accepted tag observations correct that same state.

delta = _inverse(self.fk) @ fk
rotation = self.pose[:3, :3].copy()
transition = np.eye(6)
transition[:3, 3:] = -_skew(rotation @ delta[:3, 3])
self.pose = self.pose @ delta
self.covariance = transition @ self.covariance @ transition.T + noise

Because this predictor uses measured FK increments rather than estimated velocities, its FK-noise parameters control covariance growth per unit time. Accordingly, the acceleration-noise and initial-velocity fields are unused. This preserves continuity through brief tag gaps, but it does not identify or remove an underlying calibration bias.

Visual correction and rejection

Although their prediction models differ, both filters use a visual pose to correct the predicted state. For the cube, this measurement is the fused cube-face pose, whereas for the tool it is the detected marker pose transformed through its mounting calibration. Each filter then compares the measured pose with its prediction. In the equations below, V denotes measurement covariance, while R denotes orientation:

\begin{aligned} r &=\begin{bmatrix}p_{\mathrm{meas}}-\hat p^-\\ \operatorname{Log}\!\left(R_{\mathrm{meas}}(\hat R^-)^\top\right)^\vee\end{bmatrix}\\ V &=\operatorname{diag}(\sigma_p^2 I_3,\sigma_\theta^2 I_3)\\ H_{\mathrm{cube}} &=\begin{bmatrix}I_6 & 0_6\end{bmatrix}, \qquad H_{\mathrm{tool}}=I_6\\ S &=HP^-H^\top+V,\qquad d^2=r^\top S^{-1}r\\ K &=P^-H^\top S^{-1},\qquad \delta x=Kr \end{aligned}

In this residual, the rotation logarithm expresses the orientation disagreement as a three-component rotation vector. Because the innovation covariance includes uncertainty in both the prediction and the measurement, the Mahalanobis gate tests the disagreement relative to that uncertainty rather than against a fixed distance threshold. Thus, an observation is accepted only when its squared Mahalanobis distance d^2 is within the configured innovation gate. Rejected observations do not reset the time since the last accepted measurement, and duplicate camera timestamps do not trigger a second correction.

Once an observation is accepted, the cube filter applies the full correction to pose and velocity. The tool filter, in contrast, scales its gain and correction together so that a single update cannot exceed either correction limit. This reduces abrupt feedback changes when a tag is reacquired, although it also means that a genuine large correction takes longer to absorb:

\begin{aligned} \alpha &=\min\left(1,\frac{c_p}{\max(\lVert\delta p\rVert,\varepsilon)}, \frac{c_\theta}{\max(\lVert\delta\theta\rVert,\varepsilon)}\right)\\ K_{\mathrm{tool}} &\leftarrow\alpha K_{\mathrm{tool}}, \qquad \delta x_{\mathrm{tool}}\leftarrow\alpha\delta x_{\mathrm{tool}}, \qquad \varepsilon=10^{-12}\\ \hat p^+ &=\hat p^-+\delta p,\qquad \hat R^+=\operatorname{Exp}([\delta\theta]_\times)\hat R^- \end{aligned}

Both implementations use the Joseph covariance update to reduce numerical loss of covariance symmetry and positive semidefiniteness. After correcting orientation, the filter resets the error coordinates with the SO(3) left Jacobian. Finally, explicit symmetrization removes any round-off asymmetry:

\begin{aligned} \widetilde P &=(I-KH)P^-(I-KH)^\top+KVK^\top\\ G &=I,\qquad G_{\theta\theta}=J_l(\delta\theta)\\ P^+ &=G\widetilde P G^\top,\qquad P^+\leftarrow\tfrac12\left(P^++(P^+)^\top\right) \end{aligned}

Missing measurements and controller behaviour

Although the cube filter can predict through a short detection gap, the approach controller still commands zero velocity when the current cube observation is missing, stale or rejected by the EKF. In other words, the existence of a prediction does not authorize motion towards a target whose current pose has not been visually validated. If the prediction expires, the next valid observation initializes a new cube track.

The tool tracker has encoder-derived motion information, so it can continue from FK increments during a brief tag gap without switching to absolute FK. Nevertheless, a visual correction is rejected when the camera and robot-state timestamps differ by more than the configured skew limit. If accepted tag updates stop for too long, or the largest eigenvalue of either pose-covariance block exceeds its configured variance limit, the tool estimate becomes unavailable and requires a reset or restart. Before the first accepted tag update, the timeout is measured from FK initialization.

Configuration and uncertainty

These prediction and correction behaviours depend on the settings below. In particular, a larger measurement variance reduces the influence of an individual tag observation, whereas greater process noise increases uncertainty during prediction and generally gives new measurements more influence. Since hardware sensor noise has not been measured, the listed values remain tuning assumptions rather than experimentally identified noise levels.

In simulation, telemetry plots the estimated pose against the true pose and shades the marginal intervals \pm2\sqrt{P_{ii}}. Because these bands come from the filter covariance, they describe its assumed uncertainty rather than guaranteed error bounds. When a filter is disabled, the telemetry instead shows the unfiltered pose used by the controller, without an EKF uncertainty band.

This distinction is especially important for systematic errors: neither filter estimates camera extrinsics or a separate bias state. Smoother measurements therefore do not establish that a calibration error has been corrected. The results section examines accuracy and uncertainty in the saved simulation traces, while distinguishing measured errors from claims that would require controlled trials.

The implementation is available in the cube EKF, the tool EKF, the tool tracker and the controller. The estimator configuration and simulation telemetry define the settings and recorded outputs.

CONTROL

Visual feedback, constrained motion.

Once a valid pose is available, the controller expresses the desired grasp or transfer pose relative to the current tool pose. PBVS then turns the resulting six-dimensional error into a Cartesian velocity command and uses the Jacobian to obtain joint velocities. Because the marker geometry already supplies metric position and orientation, this pose-based formulation allows us to specify the approach distance and tool alignment directly. The optional joint-space MPC builds on the same PBVS reference by adding constrained look-ahead.

The error e=[e_p^\top\;e_R^\top]^\top contains the desired tool-origin displacement in current tool axes and the rotation vector from the current orientation to the desired one. The bounded operator limits translation and rotation separately before the damped inverse maps them into joint motion.

u_{\mathrm{ref}}=J^\top(JJ^\top+\lambda^2 I)^{-1}\operatorname{bounded}(k_p e)
\mathcal J_{\mathrm{MPC}}=\sum_{i=0}^{N-1}\left( w_{\mathrm{tracking}}\lVert u_i-u_{\mathrm{ref}}\rVert^2 +w_{\mathrm{smoothing}}\lVert u_i-u_{i-1}\rVert^2\right)

When MPC is enabled, it optimizes a sequence of joint velocities but applies only the first command before solving again from the next measured state. In doing so, it balances reference tracking against abrupt velocity changes, while constraints account for joint bounds and predicted clearance.

The checked-in controller selects pure_pbvs. This avoids an iterative optimization solve, but it also means that obstacle and self-collision clearance are not checked during approach. Although pickup and placement have separate geometric guards, neither mode is a safety-rated motion controller.

For the optional MPC, the defaults are a time step of \Delta t=0.05\,\mathrm{s}, an eight-step horizon, tracking and smoothing weights of 1.0 and 0.15, a velocity limit of 0.35 rad/s, an acceleration limit of 1.5\,\mathrm{rad}/\mathrm{s}^2, and a clearance of 0.015 m with an additional 0.003 m buffer. Because the backend and runtime settings can override these values, they describe the default configuration rather than every run. They should not be interpreted as measured performance or evidence of optimal tuning.

At the task level, pickup proceeds through approach, opening, dwell, descent, close and lift. Placement, in turn, acquires one fresh destination pose and holds it fixed through raise, transfer, descent, release and retreat. Holding the target fixed avoids reacting to later detection jitter, although it assumes that the destination marker and camera remain stationary. The marker defines the placement plane, while the separate table geometry remains part of collision checking. Together, these phases define a sequence of local motions. They do not, however, provide a global plan for detouring around obstacles.

Gain and weight selection

The PBVS implementation uses a proportional gain of k_p=1.2 and Jacobian damping of \lambda=0.025. Both approach and transfer use these constructor defaults, which are not exposed in the controller JSON. To understand their roles, consider the local, unsaturated model:

\dot e\approx-k_p e,\qquad e(t)\approx e(0)e^{-k_p t},\qquad \tau=\frac1{k_p}\approx0.83\,\mathrm{s}

This time constant characterizes the ideal local response. In practice, however, it should not be treated as a measured settling time. Increasing the gain would make that response faster, but would also amplify pose noise and sensitivity to delay. To bound the resulting request, the implementation limits the linear and angular components of the twist before converting them to joint velocities.

v_{\mathrm{cmd}}=\frac{k_p e_p}{\max(1,k_p\lVert e_p\rVert/v_{\max})}, \qquad \omega_{\mathrm{cmd}}=\frac{k_p e_R}{\max(1,k_p\lVert e_R\rVert/\omega_{\max})}

At the configured approach limits of 0.06 m/s and 0.3 rad/s, saturation starts above 50 mm of translation error or 0.25 rad of rotation error. Transfer uses cartesian_speed_m_s in the sequence configuration, currently 0.03 m/s, giving a 25 mm translation-error crossover. These Cartesian caps are only part of the command path, however, so joint limits, geometry or acceleration limiting can further reduce the achieved speed.

In addition to limiting speed, the controller uses damping to reduce sensitivity to small Jacobian singular values. For a singular value \sigma_i, the inverse gain becomes:

\frac{\sigma_i}{\sigma_i^2+\lambda^2} \quad\text{instead of}\quad \frac1{\sigma_i}

The damped inverse therefore trades exact Cartesian tracking for bounded sensitivity near singular configurations. This addresses a numerical control problem, however, rather than guaranteeing a collision-free path.

Beyond the PBVS gain and damping, the optional MPC uses tracking and smoothing weights of 1.0 and 0.15. The tracking term penalizes departures from the bounded PBVS joint-velocity reference, whereas the smoothing term penalizes changes between successive commands, starting from the measured joint velocity. Increasing the smoothing weight therefore generally favours gentler command changes at the expense of reference tracking. With eight steps of 0.05 s, the default horizon covers 0.4 s. These choices express the intended tracking-versus-smoothness trade-off, but no published parameter sweep establishes an optimum.

Tracking and settling criteria

To decide when a motion phase is complete, the controller evaluates the translation-error and rotation-vector magnitudes. The approach controller declares arrival below 3 mm and 0.025 rad, whereas the placement controller advances a motion phase below 1.5 mm and 0.02 rad. Pickup additionally requires its own dwell and grasp checks. Because all of these decisions depend on the available feedback, their tolerances do not guarantee the same accuracy relative to ground truth.

\begin{aligned} E_p &=\sqrt{\frac1N\sum_{k=1}^{N}\lVert e_{p,k}\rVert^2}, & E_R &=\sqrt{\frac1N\sum_{k=1}^{N}\lVert e_{R,k}\rVert^2}\\ t_s &=\min\left\{t_k: \lVert e_{p,j}\rVert\le\varepsilon_p,\quad \lVert e_{R,j}\rVert\le\varepsilon_R \text{ for all }j=k,\ldots,N\right\} \end{aligned}

For evaluation, however, reaching a tolerance once is different from remaining within it. Settling time for a fixed target must therefore be measured over a declared observation interval, rather than inferred from a successful phase transition. If the error never stays within both tolerances, settling has not been demonstrated in that interval.

Command effort and active limits

Tracking error alone does not describe how aggressively the robot moves, so evaluation also needs a measure of command effort. Because the controller commands velocity rather than torque, we summarize that effort using squared joint velocity and command variation. These quantities are motion proxies, however, not measures of mechanical work or energy:

\begin{aligned} E_u &=\sum_k\lVert u_k\rVert^2\Delta t_k, & E_{\Delta u}&=\sum_{k=1}^{N}\lVert u_k-u_{k-1}\rVert^2\\ f_{\mathrm{sat}} &=\frac1N\sum_{k=1}^{N} \mathbf1\!\left[\lVert u_k\rVert_\infty\ge0.99u_{\max}\right] \end{aligned}

Calculating these metrics requires commands recorded at the control rate together with the effective limits for the run. The published archives contain pose telemetry and sparse phase diagnostics, but not complete control-rate command histories. We therefore make no numerical claim about command effort or the saturation fraction. Moreover, placement applies acceleration clipping even in pure PBVS mode, so a smooth command alone does not establish that MPC was active.

SIMULATION RESULTS

Recorded accuracy and uncertainty.

Eight saved simulation traces are published below, together with their original plots and CSVs. Runs 1–4 are low-noise trials with different cube and destination positions, as reported by the experimenter. The no-EKF trace records unfiltered feedback, while run 5 contains filtered feedback but has no verified configuration snapshot. H1 and H2 have archived settings and completion diagnostics. These traces document observed behaviour, but they are not a randomized or matched EKF-on/off benchmark.

The archive manifest records provenance and missing information. In particular, no run records its source commit, and the exact settings for the numbered and no-EKF traces are unavailable. Consequently, the current configuration tables elsewhere on this page must not be treated as the settings used for every result.

How the errors are calculated

For each available pose, position error is the Euclidean distance between the recorded estimate and simulator truth, while orientation error is the magnitude of the recorded world-axis rotation vector. The table reports the square root of the mean squared error magnitude over finite samples, with equal weight per row. Tool metrics include the feedback sources used during the run, including FK where applicable. Cube metrics exclude latched_pick_target, since a frozen grasp reference is not an estimate of the moving cube. Missing samples are neither interpolated nor counted as zero error.

The recording spans below use simulation time, not wall-clock execution time. Likewise, the number of available cube samples measures telemetry coverage, not the detector success rate. The calculations can be reproduced using the analysis script, and the complete numerical summary includes per-source errors, uncertainty coverage, endpoint positions and CSV checksums.

Across runs 1–4, the tool-position RMSE ranges from 0.219 to 0.327 mm, and the orientation RMSE ranges from 0.118° to 0.222°. The available cube estimates have position RMSEs of 0.158–0.378 mm. Why the cube uncertainty band ends early

In run 1, the last recorded cube estimate is at 3.25 s, although simulator truth continues to 21.20 s. Across runs 1–4, only 12.8–25.5% of rows contain a cube estimate. Consequently, the disappearing band does not mean that uncertainty becomes zero or that the cube stops moving. It means that the CSV no longer contains a current estimate or covariance.

The telemetry recorder requires a cube estimate with the current timestamp and otherwise records it as unavailable. This explains how the plot can retain truth while omitting an estimate during later action phases. The CSV alone cannot distinguish every missing detection from a phase that no longer supplies an updated cube estimate. Therefore, these traces do not validate continuous visual tracking of the cube during transport.

Unfiltered feedback and the frozen pickup target

The no-EKF trace contains 58 live cube-tag observations over 0–2.85 s. Their position RMSE is 0.252 mm and their orientation RMSE is 0.491°. It then records 110 samples of a frozen pickup target through 8.35 s. Comparing that fixed reference with the moving cube gives a 17.161 mm position RMSE, but that is not camera detection error. Combining the two sources would produce a misleading 13.887 mm aggregate. The results table therefore excludes the frozen target from the cube estimate metric.

For the tool, the same trace alternates between raw tag feedback and FK. The 230 raw-tag samples have a position RMSE of 0.942 mm, while the 197 FK samples have an RMSE of 1.879 mm. One additional sample uses FK fallback. Their combined tool RMSE is 1.453 mm, but the sources are active at different times, so this is not a controlled comparison of tag sensing with FK.

The filtered low-noise plots look smoother than the unfiltered trace. Nevertheless, their settings, paths and observation windows are not fully matched, and even the raw cube-position RMSE overlaps the filtered range. The evidence therefore supports describing the recorded estimates and their continuity, rather than claiming a particular percentage improvement caused by filtering.

Uncertainty is conservative in these simulations

Every finite covariance sample in all seven filtered traces contains the corresponding error within the plotted ±2σ interval on each individual position and rotation axis. This is 100% empirical marginal coverage for those recorded samples, not a joint confidence level or a guarantee for future runs.

The bands are also much wider than the observed errors. For example, run 1 has a median marginal position standard deviation of 18.902 mm for the cube and 6.605 mm for the tool, whereas their three-dimensional position RMSEs are only 0.273 and 0.284 mm. Its median marginal rotation standard deviations are approximately 1.25° and 1.20°, compared with orientation RMSEs of 0.553° and 0.144°. Although marginal standard deviations and vector RMSEs are different quantities, the gap is substantial. The archived per-axis statistics support the same interpretation.

Accordingly, the covariance appears conservative relative to the errors encountered in this simulated sample. This does not prove that the estimator is equally conservative under calibration bias, severe occlusion or hardware noise. The next tuning step would be to estimate measurement and prediction residuals on separate calibration data, then test accuracy, lag and uncertainty coverage on held-out runs rather than shrinking the covariance merely to fit these plots.

Higher recorded noise and sequence completion

H1 and H2 are directly linked to their archived configuration snapshots and diagnostic excerpts. Both use pure_pbvs, both EKFs and noise seed 42. Their joint-position noise standard deviation is 0.003 rad, joint-velocity noise is 0.01 rad/s and RGB pixel noise is 10.0. These are ten times the corresponding current default values. The depth-noise settings remain 0.0002 m plus a distance-dependent term of 0.0005 m/m². Thus, “higher noise” here refers specifically to the recorded encoder and RGB settings, not to a uniform increase in every sensor-noise term.

The tool-position RMSE rises to 1.774 mm in H1 and 1.781 mm in H2, with orientation RMSEs of 0.446° and 0.450°. Both diagnostic excerpts report completed pickup and placement, and their recording spans are 19.80 and 20.55 s. This demonstrates completion in these two recorded simulations, but not a general success rate. They share a seed, are not established independent repetitions and have no recorded source commit. Run 5 has a similarly sized tool-position RMSE of 1.869 mm, although its noise level cannot be inferred from that error alone.

H2 also illustrates the difference between estimation error and control error. Its sparse transfer diagnostics report the tool-to-target position error decreasing from 190.7 mm at 0.1 s to 14.2 mm at 6.1 s and 4.1 mm at 8.1 s. Those are feedback tracking errors, not errors against simulator truth. Since the diagnostics are not recorded at every control update, they cannot establish exact settling time, peak command effort or a saturation fraction. The published H2 diagnostic excerpt preserves these observations for inspection.

REPRODUCIBILITY

Start with simulation.

To reproduce the simulation, start from the repository root using the commands below. The supplied setup guide targets Ubuntu and Python 3.12, and MuJoCo requires a working graphics backend even for headless RGB-D perception.

git clone https://github.com/caseinova/robotic_studio_1.git
cd robotic_studio_1
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
python run.py --backend simulation --task pick --validate
python run.py --backend simulation --task pick
python run_sequence.py drop_zone_b --backend simulation --validate
python run_sequence.py drop_zone_b --backend simulation

Windows: use venv\Scripts\activate. Before starting the desktop launcher, complete the environment setup above and install requirements-gui.txt. Then run python run_experiments.py. Complete the separate hardware setup and calibration before using its Hardware tab. For software checks, install pytest and run python -m pytest tests. Note, however, that some tests require additional rendering or device dependencies.

Always specify --backend simulation: the sequence CLI otherwise defaults to hardware. To vary trials, change cube position / quaternion in config/simulation_config.json and the seed / noise in config/noise_config.json. Afterwards, save the exact configuration and restart the run. Do not treat random measurement noise as random object placement.

Hardware is a separate installation workflow.

This is research software, not a safety-rated controller. Follow hardware setup and calibration before motion. Keep the physical emergency stop available and verify stopping on the pendant. The desktop Stop button is cooperative software shutdown.
