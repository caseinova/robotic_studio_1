Vision-Guided Pick-and-Place Manipulation with Pose Estimation and Visual Servo Control

Abstract

Vision-guided manipulation requires reliable pose feedback despite measurement noise and intermittent marker visibility. I developed a pick-and-place system for a UR3e robot and an OnRobot RG2 gripper using a fixed RGB-D camera and ArUco markers. The system combines depth-validated marker observations with calibrated frame transformations to locate a cube and a destination marker. Separate extended Kalman filters estimate the cube and tool poses, with the tool predictor using forward-kinematic increments from joint feedback. Position-based visual servoing generates bounded joint-velocity commands, while a phase-based controller coordinates approach, grasping, transfer and release. A shared software architecture supports both MuJoCo simulation and physical hardware.

I evaluated twelve simulation trials across four initial cube positions under low-noise filtered, high-noise filtered and matched high-noise unfiltered conditions. All twelve recorded sequences completed pickup and placement. Under matched high noise, filtering reduced recorded tool-position root-mean-square error by 27.8–53.2% and orientation error by 57.7–63.5% across the four layouts. However, final horizontal placement offsets did not improve consistently, indicating that lower feedback error alone does not determine the final resting position. Three physical demonstrations additionally show cube acquisition and transfer to destination markers through the release phase. These results demonstrate integrated operation and reduced estimation error under the tested simulated noise conditions, but do not establish a general success rate or independently measured hardware accuracy. The simulation comparison uses one noise seed, and detailed physical runs will be provided in the demonstration video.

Keywords: visual servoing, extended Kalman filter, RGB-D sensing, ArUco markers, robotic manipulation.

Kinematic and state-space models

Because the application commands joint velocities rather than motor torques, I use a kinematic model to relate the measured joint angles to the tool pose and Cartesian motion. The backend handles low-level actuation, which keeps the online model small. This simplification nevertheless assumes that the commanded velocities are tracked sufficiently well over each control interval.

Forward kinematics

The UR3e has six revolute joints, represented by q \in \mathbb{R}^6. On hardware, the controller calculates the tool pose using standard Denavit–Hartenberg (DH) parameters, whereas in simulation it uses the MuJoCo robot model. In either case, forward kinematics (FK) gives the pose of the tool reference frame. The hardware uses a measured rigid offset to locate the grasp point between the fingers, as shown below. In simulation, the articulated fingers also make that grasp offset depend on opening width, so it is not constant throughout a grasp.

\begin{aligned} \theta_i &= q_i + \mathrm{offset}_i \\ A_i(q_i) &= R_z(\theta_i)\,T_z(d_i)\,T_x(a_i)\,R_x(\alpha_i) \\ {}^W T_T(q) &= {}^W T_{\mathrm{base}} \left(\prod_{i=1}^{6} A_i(q_i)\right) {}^F T_T \\ {}^W T_G(q) &= {}^W T_T(q)\,{}^T T_G \end{aligned}

The following simplified excerpt from hardware/hardware_kinematics.py builds the hardware transform chain:

for theta, a, d, alpha in zip(q + offsets, dh.a, dh.d, dh.alpha):
    ct, st = np.cos(theta), np.sin(theta)
    ca, sa = np.cos(alpha), np.sin(alpha)
    link = np.array([[ct, -st*ca,  st*sa, a*ct],
                     [st,  ct*ca, -ct*sa, a*st],
                     [ 0,     sa,     ca,    d],
                     [ 0,      0,      0,    1]])
    chain.append(chain[-1] @ link)
world_from_tool = chain[-1] @ flange_from_tool

In this excerpt, ct, st, ca and sa are the corresponding cosine and sine values. DH values and installation transforms must match the physical arm.

Velocity model

Once the tool pose is known, the controller also needs to relate joint motion to tool motion. The Jacobian provides this local velocity relationship:

\begin{aligned} {}^W V_T &= J(q)\dot q, & J_i &= \begin{bmatrix}z_{i-1}\times(p_T-p_{i-1})\\z_{i-1}\end{bmatrix} \\ {}^T V_T &= \operatorname{diag}(R^\top,R^\top)\,{}^W V_T, & R &= {}^W R_T \\ J_T(q) &= \operatorname{diag}(R^\top,R^\top)J(q) \end{aligned}

The hardware implementation calculates a Jacobian column for each revolute joint, while the simulation obtains the Jacobian from MuJoCo. During approach and transfer, the Jacobian and pose error are both expressed in the tool frame so that the requested translation and rotation use the same axes. Here, changing the expression frame rotates the axes used to express the twist without moving its origin.

linear = np.cross(axes.T, (tool[:3, 3, None] - origins).T).T
rotation = tool[:3, :3].T if local else np.eye(3)
J = np.vstack((rotation @ linear, rotation @ axes))

Discrete-time prediction and controllability

For prediction over several control intervals, the optional MPC integrates piecewise-constant joint-velocity commands. This extends the local kinematic model into a short-horizon trajectory, allowing the controller to predict joint-limit crossings and evaluate geometric clearance without identifying masses, inertias or actuator torques. Because the model remains kinematic, however, it cannot predict contact forces or compensate for arbitrary actuator dynamics.

\begin{aligned} q_{k+1} &= q_k + \Delta t\,u_k, & y_k &= q_k \\ A &= I_6, & B &= \Delta t\,I_6, \qquad C=I_6 \\ \mathcal C &= \begin{bmatrix}B & AB & \cdots & A^5B\end{bmatrix}, & \mathcal O &= \begin{bmatrix}C\\CA\\\vdots\\CA^5\end{bmatrix} \\ \operatorname{rank}(\mathcal C) &= \operatorname{rank}(\mathcal O)=6, & \Delta t &>0 \\ \sigma_i(\mathcal C) &= \sqrt6\,\Delta t, & \sigma_i(\mathcal O) &= \sqrt6,\quad i=1,\ldots,6 \end{aligned}

At \Delta t=0.05\,\mathrm{s}, every singular value of \mathcal C is approximately 0.1225 and every singular value of \mathcal O is approximately 2.4495. Both matrices therefore have a condition number of 1 in these coordinates: every joint-state direction is actuated and directly measured in this ideal model. Nevertheless, these joint-space properties do not guarantee Cartesian reachability, collision-free motion or accurate physical tracking.

integration = np.kron(np.tril(np.ones((horizon, horizon))) * dt,
                      np.eye(6))
q_predicted = np.tile(q, horizon) + integration @ u

The code constructs the same stacked prediction inside JointSpaceMPC, using the joint positions q measured at the start of each solve.

At a fixed configuration, the locally achievable Cartesian velocities lie in the column space of J(q). Thus, all six twist directions are available only when \operatorname{rank}J(q)=6. At a singularity, this rank falls, even though the ideal joint integrator remains controllable. Damping limits numerical amplification near such configurations, but cannot restore a missing motion direction.

Cube state-space model

Unlike the arm, the cube has no encoder feedback, so its short-term motion must be inferred from successive camera observations. I use a constant-velocity model to describe that motion with few states, while process noise allows for departures from the approximation during manipulation or disturbances.

\begin{aligned} x &= (p,R,v,\omega), \qquad \delta x = \begin{bmatrix}\delta p^\top & \delta\theta^\top & \delta v^\top & \delta\omega^\top\end{bmatrix}^\top \in \mathbb R^{12} \\ p_{k+1} &= p_k+\Delta t\,v_k, \qquad R_{k+1}=\operatorname{Exp}([\omega_k]_\times\Delta t)\,R_k \\ v_{k+1} &= v_k, \qquad \omega_{k+1}=\omega_k \end{aligned}

For one translation axis, the following local linearization relates position and velocity to a position measurement:

\begin{aligned} A_p &= \begin{bmatrix}1 & \Delta t\\0 & 1\end{bmatrix}, & C_p &= \begin{bmatrix}1 & 0\end{bmatrix} \\ \mathcal O_p &= \begin{bmatrix}C_p\\C_p A_p\end{bmatrix} =\begin{bmatrix}1 & 0\\1 & \Delta t\end{bmatrix}, & \det(\mathcal O_p)&=\Delta t \end{aligned}

Thus \operatorname{rank}(\mathcal O_p)=2 when \Delta t\ne0. The corresponding rotation model uses a local error-state linearization. Both analyses assume accepted measurements and valid calibration, so the result should not be interpreted as a global nonlinear observability guarantee.

Local observability analysis

For the complete cube error state, two pose observations make all twelve local state directions observable near zero angular motion. With the state ordering above, the corresponding matrices are:

\begin{aligned} F_0 &=\begin{bmatrix}I_6 & \Delta t I_6\\0 & I_6\end{bmatrix}, & H_{\mathrm{cube}} &=\begin{bmatrix}I_6 & 0\end{bmatrix}\\ \mathcal O_{\mathrm{cube}} &=\begin{bmatrix}H_{\mathrm{cube}}\\H_{\mathrm{cube}}F_0\end{bmatrix} =\begin{bmatrix}I_6 & 0\\I_6 & \Delta t I_6\end{bmatrix}, & \operatorname{rank}\mathcal O_{\mathrm{cube}} &=12\quad(\Delta t\ne0). \end{aligned}

This rank calculation establishes local identifiability in the noise-free linearization, not reliable velocity estimates from arbitrarily close or noisy samples. During occlusion, prediction supplies no new visual information. Process noise accumulates, although rotation and covariance coupling mean that not every individual variance must increase monotonically. The six-state tool filter described below instead uses H_{\mathrm{tool}}=I_6, making its pose directly observable from an accepted tag pose under known calibration. FK increments supply motion information between those observations, but do not independently identify an absolute camera-to-base bias. Neither observer includes extrinsics as states. Finally, the free cube observer has no commanded input, so I do not claim controllability of the cube before grasp contact.

RGB-D sensing and coordinate transformations

The models above require measurements of both the cube position and its orientation. I obtain these from known square markers, which provide geometric references without requiring a trained object detector. Placing markers on several faces improves the chance that at least one remains visible, while the depth image provides a metric consistency check. In return, the method depends on the specified marker dimensions, mounting transforms and depth quality.

Camera measurements and projection model

On hardware, the RealSense D435i aligns the depth image with the colour image, after which the hardware interface rectifies both images and converts the depth values to metres. The simulation supplies registered RGB-D images for the same processing pipeline, while joint positions are measured separately.

K_{\mathrm{cam}}=\begin{bmatrix}f_x & 0 & c_x\\0 & f_y & c_y\\0 & 0 & 1\end{bmatrix}, \qquad \rho=K_{\mathrm{cam}}^{-1}\begin{bmatrix}u_{\mathrm{px}}\\v_{\mathrm{px}}\\1\end{bmatrix}, \qquad {}^C p=z\rho

z is optical-axis depth, not Euclidean range. The processor also checks RGB and depth timestamps for skew and repeated frames. The IMU, meanwhile, is not used in this pipeline.

Marker pose estimation

OpenCV detects markers from the DICT_4X4_50 dictionary, using AprilTag corner refinement and a subpixel fallback. The cube uses IDs 0 and 2–6, and the tool uses ID 1. I configured the hardware perception model for a 64 mm cube with 40 mm markers on both the cube and tool.

\begin{aligned} {}^C p_j &= R\,{}^M p_j+t, \qquad \hat u_j=\pi(K_{\mathrm{cam}}\,{}^C p_j) \\ e_{\mathrm{rms}} &= \sqrt{\frac14\sum_{j=1}^{4}\lVert\hat u_j-u_j\rVert^2} \end{aligned}

A perspective-n-point (PnP) solve first estimates pose from the known square and its image corners. To incorporate depth, the processor fits a plane to samples inside an eroded marker polygon, reducing contamination from the surrounding surface. It then intersects the corner rays with that plane to obtain metric 3D corners and refines the pose through a rigid fit based on singular value decomposition (SVD). Throughout this process, reprojection checks ensure that both the initial and refined poses remain consistent with the image.

\begin{aligned} n^\top p &= d, & p_j &=\frac{d}{n^\top \rho_j}\,\rho_j \\ \ell_j &=\lVert p_{j+1}-p_j\rVert, & |\ell_j-s| &\le 0.1s \end{aligned}

The fit requires at least 16 valid depth samples and approximately 80% plane inliers: the exact threshold is the larger of 16 and the integer floor of 0.8 times the sample count. Ray-plane intersections must have finite, positive depth and a nonzero denominator. The plane tolerance adapts to depth scatter: the configured tolerance is its minimum, and the adaptive component is capped at 10% of the marker size. In addition, all four reconstructed edges must pass the size test. Together, these checks reject detections that resemble valid markers in the image but have inconsistent 3D geometry. Consequently, a bent tag or unreliable depth can interrupt tracking even when the marker ID is visible.

plane_tolerance = max(depth_tolerance,
                      min(3 * depth_sigma, marker_size * 0.1))
edge_lengths = np.linalg.norm(corners_3d - np.roll(corners_3d, -1, axis=0), axis=1)
if np.any(np.abs(edge_lengths - marker_size) > marker_size * 0.1):
    return reject("tag_metric_size_inconsistent")

Multi-marker fusion and frame transformations

Once the individual marker poses pass these checks, each accepted face is transformed to the cube centre using its mounting transform. Because that transform encodes both the marker orientation and its offset, an incorrect mounting specification introduces a bias before fusion even begins.

\begin{aligned} {}^C T_{B,i} &= {}^C T_{M_i}\,({}^B T_{M_i})^{-1}, & w_i &\propto \frac{\mathrm{area}_i}{1+e_i^2} \\ \bar p &= \sum_i w_i p_i, & \bar R &= \operatorname{proj}_{\mathrm{SO}(3)}\!\left(\sum_i w_iR_i\right) \end{aligned}

For fusion, the highest-weight face serves as the reference, and other faces contribute only if they agree with it within 20 mm and 0.35 rad. Additionally, the processor requires valid depth within the estimated cube volume. Although a single valid face can be sufficient, any accepted faces are combined into one measurement per frame for the EKF. This reduces dependence on a particular viewpoint, but it is not a majority vote: all faces share the same camera and may therefore share systematic errors. Nor can filtering rescue a frame in which every face fails the geometric checks.

\begin{aligned} {}^W T_B &= {}^W T_C\,{}^C T_B \\ {}^C T_T &= {}^C T_{M_T}\,({}^T T_{M_T})^{-1} \\ {}^T T_B &= ({}^C T_T)^{-1}\,{}^C T_B \end{aligned}

In these equations, W denotes the world, C the camera, B the cube, T the tool and M a marker. The transform {}^A T_B maps coordinates from frame B into frame A. A common camera-to-world transform cancels algebraically when the two world poses are constructed by left-multiplying these same camera-frame poses. Independently filtered states, FK initialization or fallback, asynchronous measurements and mounting errors do not generally satisfy that exact cancellation condition.

The face weights use the numerical reprojection error in pixels, so the constant 1 in their denominator corresponds to a one-pixel error scale. They are normalized heuristic quality weights, not inverse-covariance weights from a statistically optimal sensor-fusion model.

Camera-to-base calibration

To connect these camera-frame measurements to the robot, the hardware calibration workflow first imports the camera's factory intrinsics and depth scale. It then pairs stationary tool-marker observations from diverse arm poses with robot joint measurements to solve the camera-to-world and tool-marker transforms. Varying both the arm position and orientation helps distinguish the fixed camera transform from the marker mounting transform, while held-out poses test consistency beyond the fitted samples. The grasp tool centre point (TCP), however, must be measured separately because the marker observations do not identify the finger contact location.

I defined the world frame at the robot base. Consequently, my camera-to-world and camera-to-base transforms are identical:

Pose estimation and uncertainty propagation

Even after the geometric checks and face fusion, the measured pose can jitter while the object is stationary. The EKFs address this temporal variation by combining a predicted pose with a visual correction, weighting their disagreement by covariance rather than simply averaging successive frames. I use separate cube and tool filters because their available motion information differs: the cube is observed only by the camera, whereas tool motion can also be predicted from joint encoders. Despite these different predictors, both filters estimate pose in world coordinates without using simulation ground truth.

Cube-state prediction

Following the motion model introduced earlier, the cube filter assumes constant linear and angular velocity between observations. It stores orientation as a rotation matrix rather than three Euler angles, while a small rotation-vector error provides a local, three-dimensional representation for the covariance. This avoids Euler-angle singularities and, together with position and both velocities, gives a 12-dimensional error state:

\begin{aligned} x &= (p,R,v,\omega), \qquad \delta x=\begin{bmatrix}\delta p^\top & \delta\theta^\top & \delta v^\top & \delta\omega^\top\end{bmatrix}^\top \\ R_{\mathrm{true}} &= \operatorname{Exp}([\delta\theta]_\times)\,R \\ p^- &= p+hv, \qquad R^-=ER,\qquad v^-=v,\qquad \omega^-=\omega \\ \varphi &=h\omega,\qquad E=\operatorname{Exp}([\varphi]_\times) \end{aligned}
F=\begin{bmatrix} I_3 & 0 & hI_3 & 0\\ 0 & E & 0 & hJ_l(\varphi)\\ 0 & 0 & I_3 & 0\\ 0 & 0 & 0 & I_3 \end{bmatrix},\qquad P^-=FPF^\top+Q

Here, [\cdot]_\times is the cross-product matrix and J_l is the \mathrm{SO}(3) left Jacobian. Position errors are additive in world axes, while orientation errors multiply the estimate from the left. This is a mixed position/rotation error, not a six-dimensional SE(3) logarithm. The implementation divides each elapsed interval into steps of at most 0.05 s, although a time-step bound alone does not bound the rotation angle at arbitrary angular velocity. For each position–velocity or orientation–angular-velocity axis, it adds the following process covariance:

Q_{\mathrm{axis}}=\sigma_a^2\begin{bmatrix} \dfrac{h^3}{3} & \dfrac{h^2}{2}\\[6pt] \dfrac{h^2}{2} & h \end{bmatrix}

The linear and angular acceleration-noise parameters supply \sigma_a independently. Before prediction can begin, the first valid cube observation initializes the position and orientation, while both velocities start at zero. Accordingly, the initial pose covariance comes from the measurement variances, whereas the initial velocity covariance comes from the configured velocity standard deviations.

The displayed process covariance is exact for an integrated continuous white-acceleration model on a translation axis. It is not the covariance of one independently sampled constant acceleration over the entire step, which has different powers of time. For rotation, I reuse this block as a small-step approximation. At nonzero angular velocity, exact discretization of the linearized rotational noise would include rotation-dependent cross-covariance terms. Thus, the nonlinear mean propagation and its first-order transition matrix do not make the implemented angular noise covariance exact.

Tool-state prediction using forward-kinematic increments

For the tool, encoder feedback provides a more direct motion predictor. With prediction_model = fk_increment and the shared tag-with-FK tracker enabled, the filter maintains one pose estimate and a six-dimensional error covariance. Rather than supplying an absolute pose at every step, FK supplies the motion increment, so a briefly hidden tag does not force a jump to a potentially offset absolute FK pose. Instead, the visually corrected estimate advances with the measured arm motion as follows:

\begin{aligned} \delta x_T &=\begin{bmatrix}\delta p^\top & \delta\theta^\top\end{bmatrix}^\top\\ \Delta T_k &=(T_{\mathrm{FK},k-1})^{-1}T_{\mathrm{FK},k}\\ \hat T_k^- &=\hat T_{k-1}\Delta T_k\\[4pt] F_T &=\begin{bmatrix}I_3 & -[\hat R_{k-1}\Delta p_k]_\times\\0 & I_3\end{bmatrix}\\ Q_T &=\Delta t\,\operatorname{diag}(\sigma_{\mathrm{FK},p}^2 I_3,\sigma_{\mathrm{FK},\theta}^2 I_3)\\ P_T^- &=F_T P_T F_T^\top+Q_T \end{aligned}

The translation \Delta p_k belongs to the body-local increment \Delta T_k. At startup, a fresh tool-tag observation initializes the pose if one is available. Otherwise, FK supplies the initial pose. Subsequent accepted tag observations correct that same state.

delta = _inverse(self.fk) @ fk
rotation = self.pose[:3, :3].copy()
transition = np.eye(6)
transition[:3, 3:] = -_skew(rotation @ delta[:3, 3])
self.pose = self.pose @ delta
self.covariance = transition @ self.covariance @ transition.T + noise

Because this predictor uses measured FK increments rather than estimated velocities, its FK-noise parameters control covariance growth per unit time. Accordingly, the acceleration-noise and initial-velocity fields are unused. This preserves continuity through brief tag gaps, but it does not identify or remove an underlying calibration bias.

The diagonal Q_T is a tuned world-axis random-walk approximation, not an exact propagation of encoder uncertainty. Successive increments share an FK sample, so their measurement errors can be temporally correlated. The implementation does not track those correlations or derive a full increment covariance from the encoder Jacobians. It also initializes covariance from the configured visual measurement variances even when FK seeds the pose. These choices limit the statistical interpretation of the tool uncertainty.

Visual measurement updates and outlier rejection

Although their prediction models differ, both filters use a visual pose to correct the predicted state. For the cube, this measurement is the fused cube-face pose, whereas for the tool it is the detected marker pose transformed through its mounting calibration. Each filter then compares the measured pose with its prediction. In the equations below, V denotes measurement covariance, while R denotes orientation:

\begin{aligned} r &=\begin{bmatrix}p_{\mathrm{meas}}-\hat p^-\\ \operatorname{Log}\!\left(R_{\mathrm{meas}}(\hat R^-)^\top\right)^\vee\end{bmatrix}\\ V &=\operatorname{diag}(\sigma_p^2 I_3,\sigma_\theta^2 I_3)\\ H_{\mathrm{cube}} &=\begin{bmatrix}I_6 & 0_6\end{bmatrix}, \qquad H_{\mathrm{tool}}=I_6\\ S &=HP^-H^\top+V,\qquad d^2=r^\top S^{-1}r\\ K &=P^-H^\top S^{-1},\qquad \delta x=Kr \end{aligned}

In this residual, the rotation logarithm expresses the orientation disagreement as a three-component rotation vector. Because the innovation covariance includes uncertainty in both the prediction and the measurement, the Mahalanobis gate tests the disagreement relative to that uncertainty rather than against a fixed distance threshold. Thus, an observation is accepted only when its squared Mahalanobis distance d^2 is within the configured innovation gate. Rejected observations do not reset the time since the last accepted measurement, and duplicate camera timestamps do not trigger a second correction.

The displayed measurement Jacobians are first-order approximations about small pose errors. Rotation matrices avoid Euler-angle singularities, but the principal rotation logarithm still has an ambiguity at 180°. Moreover, a six-dimensional innovation has a chi-squared interpretation only under a correctly specified Gaussian model with the required independence assumptions. The configured gate of 25 is therefore a tuning threshold here, not a measured false-rejection probability.

Once an observation is accepted, the cube filter applies the full correction to pose and velocity. The tool filter, in contrast, scales its gain and correction together so that a single update cannot exceed either correction limit. This reduces abrupt feedback changes when a tag is reacquired, although it also means that a genuine large correction takes longer to absorb:

\begin{aligned} \alpha &=\min\left(1,\frac{c_p}{\max(\lVert\delta p\rVert,\varepsilon)}, \frac{c_\theta}{\max(\lVert\delta\theta\rVert,\varepsilon)}\right)\\ K_{\mathrm{tool}} &\leftarrow\alpha K_{\mathrm{tool}}, \qquad \delta x_{\mathrm{tool}}\leftarrow\alpha\delta x_{\mathrm{tool}}, \qquad \varepsilon=10^{-12}\\ \hat p^+ &=\hat p^-+\delta p,\qquad \hat R^+=\operatorname{Exp}([\delta\theta]_\times)\hat R^- \end{aligned}

Both implementations use the Joseph covariance update to reduce numerical loss of covariance symmetry and positive semidefiniteness. After correcting orientation, the filter resets the error coordinates with the SO(3) left Jacobian. Finally, explicit symmetrization removes any round-off asymmetry:

\begin{aligned} \widetilde P &=(I-KH)P^-(I-KH)^\top+KVK^\top\\ G &=I,\qquad G_{\theta\theta}=J_l(\delta\theta)\\ P^+ &=G\widetilde P G^\top,\qquad P^+\leftarrow\tfrac12\left(P^++(P^+)^\top\right) \end{aligned}

For this left-error convention, the positive-sign left Jacobian in the reset follows from linearizing \operatorname{Log}(\operatorname{Exp}([\delta\theta+\eta]_\times)\operatorname{Exp}(-[\delta\theta]_\times))^\vee with respect to the small remaining error \eta. This is consistent with the left-perturbation identities of Solà, Deray and Atchuthan. The Joseph expression is positive semidefinite in exact arithmetic for positive semidefinite input covariances, including when a reduced gain is used. However, the residual-dependent gain cap and rejection gate make the update nonlinear, so this covariance is an approximation rather than an exact posterior or an optimality guarantee. Symmetrization alone does not repair an indefinite matrix.

Measurement loss and feedback availability

Although the cube filter can predict through a short detection gap, the approach controller still commands zero velocity when the current cube observation is missing, stale or rejected by the EKF. In other words, the existence of a prediction does not authorize motion towards a target whose current pose has not been visually validated. If the prediction expires, the next valid observation initializes a new cube track.

The tool tracker has encoder-derived motion information, so it can continue from FK increments during a brief tag gap without switching to absolute FK. Nevertheless, a visual correction is rejected when the camera and robot-state timestamps differ by more than the configured skew limit. If accepted tag updates stop for too long, or the largest eigenvalue of either pose-covariance block exceeds its configured variance limit, the tool estimate becomes unavailable and requires a reset or restart. Before the first accepted tag update, the timeout is measured from FK initialization.

Estimator tuning and uncertainty representation

I tune the prediction and correction steps through the parameters below. Increasing measurement variance reduces the influence of an individual tag observation, whereas increasing process noise raises uncertainty during prediction and generally gives new measurements more influence. I have not measured hardware sensor noise, so I treat these values as tuning assumptions rather than experimentally identified noise levels.

For the reported trials, I assign the tool twice the cube's measurement standard deviations: 8 mm versus 4 mm for position, and 0.04 versus 0.02 rad for orientation. This gives tool observations four times the measurement variance. With the same prior covariance, increasing measurement variance reduces the correction's influence, but the cube and tool have different predictors and priors, so these numbers alone do not determine their relative Kalman gains. I use them as conservative tuning choices, not as evidence that the physical tool sensor is four times noisier. For the cube, acceleration-noise densities of 0.05 m/s3/2 and 0.1 rad/s3/2 allow velocity changes. For the tool, FK-increment noise densities of 0.002 m/√s and 0.02 rad/√s instead grow pose covariance as encoder-derived motion is integrated.

I also cap each accepted tool correction at 3 mm and 0.02 rad to limit reacquisition jumps, and bound prediction without an accepted observation to 0.3 s. These settings trade responsiveness against continuity rather than eliminating calibration error. Keeping them fixed across the noise conditions makes the matched comparisons a test of that choice: filtering reduces tool-position RMSE by 27.8–53.2% across the four high-noise layouts. However, the coverage results show conservative covariance bands, so improved RMSE alone does not establish statistically calibrated uncertainty. Further tuning would require separate training and validation trajectories, including motion and occlusion, rather than narrowing the bands until they match these same traces.

In simulation, telemetry plots the estimated pose against the true pose and shades the marginal intervals \pm2\sqrt{P_{ii}}. Because these bands come from the filter covariance, they describe its assumed uncertainty rather than guaranteed error bounds. When a filter is disabled, the telemetry instead shows the unfiltered pose used by the controller, without an EKF uncertainty band.

Even for an ideal Gaussian distribution, a marginal ±2σ interval and a three-dimensional ellipsoid with 2σ principal radii do not have the same coverage. The former contains approximately 95.45% of one component's distribution, whereas the latter contains approximately 73.85% of the joint three-dimensional distribution. The viewer's additional scale factor is purely visual. Neither the scaled ellipsoid nor these nominal Gaussian percentages establish empirical coverage for this filter.

This distinction is especially important for systematic errors: neither filter estimates camera extrinsics or a separate bias state. Smoother measurements therefore do not establish that a calibration error has been corrected. The results section examines accuracy and uncertainty in the saved simulation traces, while distinguishing measured errors from claims that would require controlled trials.

The implementation is available in the cube EKF, the tool EKF, the tool tracker and the controller. The estimator configuration and simulation telemetry define the settings and recorded outputs.

Visual servo control and motion constraints

Once a valid pose is available, the controller expresses the desired grasp or transfer pose relative to the current tool pose. PBVS then turns the resulting six-dimensional error into a Cartesian velocity command and uses the Jacobian to obtain joint velocities. Because the marker geometry already supplies metric position and orientation, this pose-based formulation allows me to specify the approach distance and tool alignment directly. The optional joint-space MPC builds on the same PBVS reference by adding constrained look-ahead.

The error e=[e_p^\top\;e_R^\top]^\top contains the desired tool-origin displacement in current tool axes and the rotation vector from the current orientation to the desired one. Specifically, the error transform is T_e=({}^W T_T)^{-1}{}^W T_{T^*}, where T^* is the desired tool frame. During approach, the equivalent product is the measured tool-from-marker transform multiplied by the inverse of the desired tool-from-marker transform. Thus, a positive translation error requests motion towards the target. The bounded operator limits translation and rotation separately before the tool-axis damped inverse maps them into joint motion:

u_{\mathrm{ref}}=J_T^\top(J_TJ_T^\top+\lambda^2 I_6)^{-1}\operatorname{bounded}(k_p e)

The Jacobian comes from encoder FK, whereas the error can come from visual feedback. Their physical tool axes must agree for this mapping to be accurate. Cancelling a common camera transform in a relative pose does not itself correct an erroneous tool mounting or Jacobian.

\mathcal J_{\mathrm{MPC}}=\sum_{i=0}^{N-1}\left( w_{\mathrm{tracking}}\lVert u_i-u_{\mathrm{ref}}\rVert^2 +w_{\mathrm{smoothing}}\lVert u_i-u_{i-1}\rVert^2\right)

When MPC is enabled, it optimizes a sequence of joint velocities but applies only the first command before solving again from the next measured state. In doing so, it balances reference tracking against abrupt velocity changes, while constraints account for joint bounds and predicted clearance.

I use pure_pbvs for the reported trials. This avoids an iterative optimization solve, but it also means that obstacle and self-collision clearance are not checked during approach. Although pickup and placement have separate geometric guards, neither mode is a safety-rated motion controller.

For the optional MPC, I set the defaults to a time step of \Delta t=0.05\,\mathrm{s}, an eight-step horizon, tracking and smoothing weights of 1.0 and 0.15, a velocity limit of 0.35 rad/s, an acceleration limit of 1.5\,\mathrm{rad}/\mathrm{s}^2, and a clearance of 0.015 m with an additional 0.003 m buffer. I allow the backend and runtime settings to override these values, so they describe my defaults rather than every run. I do not claim that these defaults are optimal or that they establish measured performance.

At the task level, pickup proceeds through approach, opening, dwell, descent, close and lift. Placement, in turn, acquires one fresh destination pose and holds it fixed through raise, transfer, descent, release and retreat. Holding the target fixed avoids reacting to later detection jitter, although it assumes that the destination marker and camera remain stationary. The marker defines the placement plane, while the separate table geometry remains part of collision checking. Together, these phases define a sequence of local motions. They do not, however, provide a global plan for detouring around obstacles.

Gain and weight selection

The PBVS implementation uses a proportional gain of k_p=1.2 and Jacobian damping of \lambda=0.025. Both approach and transfer use these constructor defaults, which are not exposed in the controller JSON. To isolate the gain's role, first assume a fixed target, small pose error, exact twist tracking, negligible damping, no saturation and no delay:

\dot e\approx-k_p e,\qquad e(t)\approx e(0)e^{-k_p t},\qquad \tau=\frac1{k_p}\approx0.83\,\mathrm{s}

This 0.83 s time constant belongs to that idealized model, not the implemented damped controller's general response or its measured settling time. The importance of the interaction model and pose-estimation accuracy in visual-servo stability is discussed by Chaumette and Hutchinson. Increasing the gain requests a faster response, but also amplifies pose noise and sensitivity to delay. To bound the request, I limit the linear and angular components of the twist before converting them to joint velocities.

v_{\mathrm{cmd}}=\frac{k_p e_p}{\max(1,k_p\lVert e_p\rVert/v_{\max})}, \qquad \omega_{\mathrm{cmd}}=\frac{k_p e_R}{\max(1,k_p\lVert e_R\rVert/\omega_{\max})}

I limit approach motion to 0.06 m/s and 0.3 rad/s, so saturation starts above 50 mm of translation error or 0.25 rad of rotation error. For transfer, I set cartesian_speed_m_s to 0.03 m/s in the sequence configuration, giving a 25 mm translation-error crossover. These Cartesian caps are only part of the command path, however, so joint limits, geometry or acceleration limiting can further reduce the achieved speed.

In addition to limiting speed, the controller uses damping to reduce sensitivity to small Jacobian singular values. For a singular value \sigma_i, the inverse gain becomes:

\frac{\sigma_i}{\sigma_i^2+\lambda^2} \quad\text{instead of}\quad \frac1{\sigma_i}

The damped inverse therefore trades exact Cartesian tracking for bounded sensitivity near singular configurations. This addresses a numerical control problem, however, rather than guaranteeing a collision-free path.

Retaining damping in the same local, frozen-Jacobian approximation gives a direction-dependent response:

\begin{aligned} \dot e &\approx-k_p J_TJ_T^\top(J_TJ_T^\top+\lambda^2 I_6)^{-1}e,\\ \gamma_i &=k_p\frac{\sigma_i^2}{\sigma_i^2+\lambda^2},\qquad \tau_i=\frac1{\gamma_i}\quad(\sigma_i>0). \end{aligned}

Each nonzero singular direction contracts in this ideal local model, but small singular values make convergence slower, and a zero singular direction has no contraction. Therefore, damping does not prove global convergence. The implementation stacks metres and radians without an explicit task-space length weighting, so singular values and the numerical damping choice depend on that unit convention. For the ideal sampled scalar response, e_{k+1}=(1-k_p\Delta t)e_k requires 0<k_p\Delta t<2 for asymptotic stability. The nominal product is 0.06, but this condition excludes sensor delay, saturation, moving targets and imperfect actuation, and is not a stability certificate for the complete task.

Beyond the PBVS gain and damping, the optional MPC uses tracking and smoothing weights of 1.0 and 0.15. The tracking term penalizes departures from the bounded PBVS joint-velocity reference, whereas the smoothing term penalizes changes between successive commands, starting from the measured joint velocity. Increasing the smoothing weight therefore generally favours gentler command changes at the expense of reference tracking. With eight steps of 0.05 s, the default horizon covers 0.4 s. These choices express the intended tracking-versus-smoothness trade-off, but no published parameter sweep establishes an optimum.

The MPC cost tracks one joint-velocity reference held constant across each solve, not a future Cartesian pose-error trajectory. Before constructing the cost, the solver scales the PBVS reference if needed to respect its uniform joint-speed limit. Its first difference is relative to the measured joint velocity, u_{-1}=\dot q_k. Linearized clearance constraints are checked again on the nonlinear geometry at discrete path samples, but this is not a continuous swept-volume guarantee. There is no terminal cost or invariant terminal set here, so I make no claim of recursive feasibility or a formal MPC closed-loop stability proof.

Tracking and settling criteria

To decide when a motion phase is complete, the controller evaluates the translation-error and rotation-vector magnitudes. The approach controller declares arrival below 3 mm and 0.025 rad, whereas the placement controller advances a motion phase below 1.5 mm and 0.02 rad. Pickup additionally requires its own dwell and grasp checks. Because all of these decisions depend on the available feedback, their tolerances do not guarantee the same accuracy relative to ground truth.

\begin{aligned} E_p &=\sqrt{\frac1N\sum_{k=1}^{N}\lVert e_{p,k}\rVert^2}, & E_R &=\sqrt{\frac1N\sum_{k=1}^{N}\lVert e_{R,k}\rVert^2}\\ t_s &=\min\left\{t_k: \lVert e_{p,j}\rVert\le\varepsilon_p,\quad \lVert e_{R,j}\rVert\le\varepsilon_R \text{ for all }j=k,\ldots,N\right\} \end{aligned}

For evaluation, however, reaching a tolerance once is different from remaining within it. Settling time for a fixed target must therefore be measured over a declared observation interval, rather than inferred from a successful phase transition. If the error never stays within both tolerances, settling has not been demonstrated in that interval.

System integration and robustness

I integrate sensing, estimation and control through timestamped robot states and RGB-D frames, then coordinate the task with explicit action phases. Approach and transfer share the selected PBVS/MPC policy. When the FK-increment tool EKF is enabled with tag feedback, the pickup action creates a shared tool tracker and passes it through approach, pickup and placement. Consequently, these actions can use the same corrected pose without resetting to absolute FK at each handover. Without that tracker, pickup and the non-transfer placement phases use FK, while approach and transfer retain their configured tag/FK selection. Encoder-based kinematics still supply the joint state, Jacobian and collision geometry in either case. A continuous feedback estimate therefore does not remove the need for consistent calibration.

Across the twelve selected trials, the logs report completed pickup and placement in all three conditions and all four layouts. Increasing measurement noise with fixed filter tuning increases tool-pose error, while enabling the filters under that same high noise reduces tool-position RMSE in every layout. Nevertheless, final XY offsets remain mixed between filtered and unfiltered runs, ranging from 0.550 to 2.149 mm over all twelve trials. Together, the pose errors and endpoints demonstrate completion under the tested noise, not a universal benefit to landing accuracy or a statistically established success rate.

Limitations of disturbance evaluation

The noise experiments perturb measurements, not actuator torque or the physical scene. Although different starting layouts exercise different trajectories, they are not disturbances applied during a run. I have not published controlled tests of external pushes, payload changes, camera drift, delayed feedback or prolonged occlusion. Likewise, latching the destination suppresses later detection jitter but prevents adaptation if the marker moves after acquisition. Pure PBVS also lacks approach collision checking, so the demonstrated paths do not establish general obstacle avoidance.

To extend this evaluation, I would repeat matched layouts over independent seeds, apply timed observation dropouts and known calibration offsets, and record recovery time, peak error, completion, minimum clearance and deadline misses. A physical disturbance test would additionally require an approved hardware procedure and independent position measurements. Until then, the evidence supports robustness to the specified simulated measurement noise, while the failure tests support bounded software responses to particular invalid inputs.

Tool-marker calibration procedure

Before collecting samples, verify calibration.world_from_base, the robot DH model, camera calibration and stream profile, and the tool marker’s ID and measured size. Use identity for world_from_base only when the world and controller base frames really coincide. Keep the camera and tag mount fixed. Confirm the flange_from_tool definition; if unset, the collector uses the nominal DH flange as the tool frame. This does not measure the grasp TCP.

# Collect into a new file
python calibrate_camera.py collect --samples my_camera_samples.json

# Optional continuation of the same, unchanged installation
python calibrate_camera.py collect --samples my_camera_samples.json --append

# Solve offline without changing the hardware configuration
python calibrate_camera.py solve --samples my_camera_samples.json --output my_camera_result.json

# After reviewing a passing result, solve and apply it
python calibrate_camera.py solve --samples my_camera_samples.json --output my_camera_result.json --write-config

Collection reads camera observations and robot joint state without commanding robot or gripper motion. Move the arm only with its approved controls, stop at each pose, and press Space in the calibration camera window to save an accepted sample. Collect at least 12 distinct poses, preferably 15–25 or more well-distributed positions with tilt around at least two axes. Q or Escape ends collection. Use --append only for a compatible continuation, not after replacing or moving the camera or changing the tag/model setup.

The solver jointly estimates world_from_camera and tool_from_marker. Review pose_count, validation_errors, fit_errors and passed in the result JSON. --write-config applies only a passing result with matching recorded metadata and saves a backup. A numerical pass is not proof of physical accuracy, so independently check known positions and orientations before motion. The hardware guide describes thresholds, rejection reasons and calibration options.

Experiment replication and data analysis

To vary a simulation, change cube position and quaternion in config/simulation_config.json and measurement noise and seed in config/noise_config.json. Use config/estimator_config.json for the independent EKF switches and tuning, and config/controller_config.json and config/sequence_config.json for action settings. Save the configuration and restart the run. Noise settings perturb measurements rather than directly applying actuator disturbances or randomizing object placement.

To repeat a reported condition, use its archived configuration files rather than assuming the current defaults are identical. No source commit was recorded for these trials, so the configurations alone cannot guarantee bit-for-bit reproduction. To regenerate the published figures from the included CSVs without launching a simulation or opening devices, run:

python docs/analyze_results.py
python -m unittest discover -s docs -p "test_*.py"

The mathematical checks compare FK and EKF Jacobians with finite differences, verify the implemented covariance propagation and PBVS mapping, and distinguish exact identities from stochastic approximations.
